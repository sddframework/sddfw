# SDDFW v0.1 acceptance specification

## Intent

Help a developer turn a small reviewed change into agent-authored checks,
implementation, and local evidence. The first integration is Playwright Test
for web interfaces and HTTP APIs. A usable source preview matters more than
an extensive framework surface.

## Acceptance criteria

| ID | Given | When | Then | Verification |
| --- | --- | --- | --- | --- |
| CLI-001 | Node.js 22+ and a clean directory | A developer installs the packaged CLI and initializes the demo | The CLI copies a runnable frontend, real backend, and tests; dependencies and Chromium can be installed with `--install` | Packaged integration journey |
| CLI-002 | An existing Playwright project | The developer initializes SDDFW | Existing application files, tests, scripts, configuration, AGENTS.md, and CLAUDE.md are preserved; the configured test directory resolves relative to its Playwright config | Core tests |
| SPEC-001 | A described change and an available coding agent | The developer drafts a specification | The agent writes observable criteria with stable IDs; unresolved decisions remain TODOs; unrelated edits stop the workflow | Core guards and live Codex trial |
| SPEC-002 | A completed, deliberately reviewed specification | The developer approves it and later changes its meaning | Approval records the normalized spec hash; an edited spec must be approved again; TODOs cannot be approved | Core and packaged integration tests |
| AI-001 | An approved specification | The developer runs the automated workflow | The local agent reuses, creates, or adapts tagged Playwright tests; SDDFW checks them against the current product before implementation | Live Codex trial |
| AI-002 | Prepared tests and useful baseline evidence | The agent implements the change | Tests and Playwright configuration remain fixed; specification, approval and SDDFW configuration stay bound to the values recorded before test preparation; protected edits stop acceptance and are preserved for review | Workflow-control guards, source snapshots and integration |
| AI-003 | Executed acceptance failures | The first implementation attempt fails | SDDFW supplies the local failure report for one additional product repair; missing, blocked, or flaky evidence stops the loop; no more than two implementation attempts occur | Real Playwright integration with an explicitly simulated agent adapter |
| EVID-001 | Tests mapped to accepted criteria | Playwright runs the suite | Every relevant mapped test must execute and pass; missing, skipped, expected-failure, flaky, and blocked checks cannot produce clean acceptance | Evidence tests and integration journey |
| EVID-002 | Frontend and API checks of a real demo backend | The developer saves, removes, repeats, or partitions favorites | The observed UI and API behavior match the five demo criteria, including persistence, idempotency, and simulated identity isolation | Demo UI/API and backend tests |
| EVID-003 | A deliberate duplicate-prevention regression | The developer verifies the demo | FAV-003 fails; restoring the implementation permits a fresh passing run | Mutation exercise and integration journey |
| EVID-004 | An executed acceptance run | The developer reviews its evidence | Local JSON, Markdown, and HTML reports record criterion results, source/spec/config context, versions, environment, declared mocks, and useful artifact references; JSON retains approval hashes | Evidence and integration tests |
| EVID-005 | A stored report | Source, spec, approval, or configuration changes | `report` refuses to present the previous result as current acceptance | Core and integration tests |
| USE-001 | No supported AI account | The developer uses manual mode or verifies existing tests | Manual mode exports usable instructions without claiming implementation; verification does not require an AI account | Core and integration tests |
| DOC-001 | A new contributor or prospective user | They open the landing or GitHub guides | They can follow a real install path, run frontend/backend examples, understand AI costs and evidence limits, and find contribution instructions | Documentation and landing review |

## Boundaries

The framework invokes a developer's installed coding agent under its existing
account and permissions. Agent calls have a 15-minute limit; Playwright runs
have a 10-minute limit. SDDFW does not provision accounts, publish packages,
deploy applications, merge changes, or upload reports automatically.

Test preparation can change assertions when the accepted behavior requires it.
That diff needs review: freezing tests during implementation does not prove
that their interpretation is correct. Hashes detect ordinary changes; they are
not a tamper-proof audit or a sandbox against a malicious local agent.

Evidence describes one historical execution in its recorded environment.
Freshness checks cover recorded local sources, specification, approval, and configuration;
they do not recheck remote services or detect undeclared mocks. Detailed logs
and traces may contain application data and need inspection before sharing.

The demo identity selector is explicitly simulated. Its checks establish data
partitioning, not production authentication or authorization. Performance,
accessibility, and security certification are outside this version's acceptance.

The source preview has no npm registry release. Codex and Claude Code adapters
are provided; actual adapter and platform validation is recorded separately in
the [validation notes](../docs/validation.md). Other runners and imports from
other spec formats are future integrations.
